# Requirements — FEAT-260912-84c828 Harry can tell you something went wrong

## Context & problem

Harry's whole design is degradation. A feed dies and the page still renders; a credential
lapses and one source falls back; a capability is half-written and the rest come up. Every
one of those is invisible when it works, which means **every one of them is invisible when
it does not.**

A morning page that lost De Tijd three weeks ago looks exactly like a morning page that had
no De Tijd article that day. A capability skipped at start-up looks exactly like one that
was never installed. There is no way to tell the difference from the thing itself, which is
why the alert is part of the design rather than a nicety.

Nothing in Harry can say anything to anybody today. `/health` carries what was skipped and
nothing watches `/health`. This is the feature every other one has been deferring to, and
three already name it by id.

It is also the first real capability in `.harry/`. Everything about the folder format —
the declaration, the generated `.env`, the credential in `.env.local`, the runbook in the
body — gets exercised for the first time by something that is not a test fixture.

## Goals

- Core can say "this went wrong" without knowing where it goes.
- It arrives in Slack.
- The same fault does not say it twice today.
- Slack being down costs you the message, not the thing that was reporting.
- A capability that did not load reaches a person, which is the case three features have
  been handing forward.

## Non-goals

- **Anything Harry receives.** Buttons, slash commands, Socket Mode, `slack_action` in the
  registry — this is one-way, out. A reply path is a second credential, a second inbound
  surface and an approval model, and none of it is needed to stop a failure being silent.
- Severities, routing, or more than one channel. One channel, one kind of message. A
  second channel is a setting when somebody wants one.
- Rich formatting. Blocks, attachments, threading. The message is read on a phone.
- Retries with backoff. One attempt, and the failure is logged. A retry loop around an
  alert is machinery that hides the thing it is reporting.
- The scheduler's deadline watchdog. It is the next feature and it calls this one.

## How core reaches a capability without naming it

Core must not know that Slack exists — that is the rule the whole layout rests on. So:

- A capability registers itself as somewhere alerts can go, with `registry.alerts(fn)`.
  That is the **fourth** registry method, and it arrives now rather than earlier because
  this is the feature that executes it. The loader's requirements page deferred
  `route`, `slack_action` and `on` on exactly that ground.
- `harry.alerts.Alerts` holds whatever registered and sends to all of them. Core pieces
  that need to report something are handed one.
- **Zero sinks is a working Harry.** With nothing registered, an alert is a WARNING in the
  log and nothing else. That is what a fresh checkout does, and it is not an error.

`Alerts` is built after loading, because the sinks are capabilities and a capability has to
load before it can carry news. The start-up skips are therefore reported once the catalogue
is complete, not while it is being built.

## Scenarios

### Scenario 1: A message arrives in Slack

```gherkin
Given a bot token and a channel
When Harry sends an alert
Then one chat.postMessage request carries the channel and the text
And the text is what the caller wrote, with nothing added
```

### Scenario 2: Core reports a fault without knowing where it goes

```gherkin
Given a connector that registered itself as an alert sink
When core raises an alert
Then that connector's function is called with the message
And `git grep` finds no capability name in src/harry/
```

### Scenario 3: Nothing registered is a working Harry

```gherkin
Given no capability registered as an alert sink
When core raises an alert
Then it is logged at WARNING
And nothing raises
```

A fresh checkout has no Slack credential. Alerting that fell over without one would make
the unconfigured case the broken case, which is backwards.

### Scenario 4: The same fault does not report twice today

```gherkin
Given an alert raised with the key "capability:icloud"
When the same key is raised again four hours later
Then nothing is sent
When it is raised again 24 hours after the first
Then it is sent
And an alert raised with no key is always sent
```

**The rule, in one sentence:** an alert carrying a `key` is sent only if that key has not
been sent in the last 24 hours. No key means no suppression, because the caller that did
not name the fault cannot have meant "this is the same one".

The record is in memory. **A restart clears it**, so a fault already reported today reports
again after a restart — which is stated rather than hidden, and is the right trade while
there is no store: Harry restarts when somebody deploys it, not once an hour. The store is
its own piece and this feature does not start it.

### Scenario 5: Slack being down costs the message, not the caller

```gherkin
Given Slack answers 500, or the connection is refused
When Harry sends an alert
Then the caller is not broken by it
And the failure is logged with what went wrong
And the next alert is still attempted
```

An alert path that raises takes down the thing that was trying to report a problem, which
is the worst possible direction for this particular code to fail in.

### Scenario 6: A capability that did not load reaches a person

```gherkin
Given a capability was skipped at start-up with a reason
When Harry finishes starting
Then one alert names the capability, its kind and the reason
And a capability that loaded produces no alert
And the key is the capability, so a restart loop does not repeat it within the day
```

This is the case FEAT-260912-8a0ab0 handed forward and the reason the seam is not
theoretical: one real caller, in this feature, exercising the whole path.

### Scenario 7: The token never appears anywhere

```gherkin
Given a bot token is configured
When Slack answers with an error that quotes the request
Then the token is in no log line, no alert and no /health field
And the committed .env carries the key with an empty value
```

## When it degrades

- **No token, or no channel** — the connector disables itself and says which setting is
  missing, the way every capability does. Harry starts. Alerts go to the log.
- **Slack unreachable, or 500, or rate-limited** — scenario 5. One attempt, logged, and the
  caller carries on. No retry loop.
- **The Slack connector itself failed to load** — nothing can alert about that, by
  construction. It is in `/health` and in the log on the machine somebody just restarted.
  Naming it here because it is the one hole this design cannot close: the thing that
  reports failures cannot report its own absence.
- **A channel that does not exist** — Slack answers `channel_not_found`. Logged, once, like
  any other failure.

## Out of scope

- The deadline watchdog, the scheduler, and anything about jobs.
- Alerting on a degraded feed or a lapsed browser session. Those arrive with the connectors
  that have them; this feature ships the path and one real caller.
- Persisting what has already been reported.
