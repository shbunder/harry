# Requirements — FEAT-260912-74f222 Anything Claude makes can land on the tablet

## Context & problem

This is where Harry's output goes. The morning page is the first thing to use it, and it is
not the only one — "put this on my tablet" is a thing you want on a Tuesday afternoon, with
a document Claude just wrote.

It also holds the most dangerous credential in the repository. **The reMarkable device token
grants complete read and write access to every document on the tablet, with no scopes and no
expiry.** There is no read-only variant to ask for. That shapes three things here: where the
token lives, what is allowed to print it, and how small the write surface is kept.

The protocol is reverse-engineered. Nobody at reMarkable promises it will keep working, and
in August 2026 a client release broke every write until it was patched. Expect that a few
times a year.

Four things were settled by spikes in September 2026 rather than by reading, and each one
changed the plan:

- **remarkapy can pair on its own.** `register_device(code)` exchanges the 8-character code
  from `my.remarkable.com/device/desktop/connect` for a permanent device token. The plan
  assumed the Go `rmapi` binary was needed for this. It is not, so the container does not
  need Go in it.
- **A push works on the free tier.** A 9,778-byte PDF was uploaded and **confirmed on the
  device** — no Connect subscription. Two implementers had disagreed about this.
- **The rendering half is not a risk.** WeasyPrint 70.0 renders 509.34 × 679.13 pt with no
  `brew install pango`.
- **Documents nobody touches are removed after 50 days** on the free tier. Irrelevant for a
  page replaced every morning; it matters the day somebody treats the tablet as an archive.

## Goals

- A PDF on disk lands in a named folder on the tablet, and Harry says where it went.
- Claude can push a document from any session — a file it has a path to, or markdown it just
  wrote.
- Claude can see what is already in the folder.
- A push that fails once is retried; a second failure reaches Slack.
- The device token never appears in a log line, an error message, or a Slack message.
- Pairing this machine, or a fresh NUC, is one command.

## Non-goals

- **Reading annotations back off the tablet.** A page you wrote on is not a thing Harry has
  been asked to do anything with. It is also where a read-heavy surface would grow.
- **Deleting, moving or renaming anything.** Harry adds. The token permits all three, which
  is exactly why the connector does not expose them.
- **Rendering the morning page.** That is FEAT-260912-0f2744. A second renderer here would be
  two renderers.
- **A Go `rmapi` binary.** The spike settled it: remarkapy does the pairing.
- Syncing, watching, or a two-way anything.

## What this offers the digest

The signature FEAT-260912-0f2744 wrote down before this connector existed:

| The digest calls | It gets back |
|---|---|
| `tablet.push(path, name)` | `{where}` — where it ended up, for the answer to quote |

The digest declares the tablet `optional:`. **A page with nowhere to push is a page on disk**,
which is what `make digest-dry` has always been for.

## Where the token lives

`.harry/connectors/remarkable/.env.local`, gitignored, one key:

```bash
cat > .harry/connectors/remarkable/.env.local <<'ENV'
DEVICE_TOKEN=<the long token>
ENV
```

**Not `~/.rmapi`**, which is where the spike left it. A file in a home directory is outside
the repository, which is the good half, and also outside the container, which is the bad
half — the NUC would have nowhere to read it from and no way to inject it. `HARRY_REMARKABLE_DEVICE_TOKEN`
is the environment name a container uses, the same as every other capability.

The token is declared `secret: true`, which is what makes `context.redact()` scrub it out of
any alert this connector raises.

## Scenarios

### Scenario 1: A PDF lands on the tablet

```gherkin
Given a PDF on disk and a configured folder name "Harry"
When Harry pushes it as "Morning page — Monday 14 September"
Then it is uploaded under that visible name, inside that folder
And the answer says the folder it landed in and the id it was given
```

### Scenario 2: The folder is made if it is not there

```gherkin
Given no folder called "Harry" on the tablet
When Harry pushes the first page
Then the folder is created once, at the top level, and the page goes inside it
And a second push that day finds the existing folder rather than making another
```

### Scenario 3: A push that fails once is retried once

```gherkin
Given the first upload attempt fails with a network error
When Harry pushes
Then it tries exactly once more, and the second attempt's success is the answer
And nothing reaches Slack, because a retry that worked is not a fault
```

### Scenario 4: A second failure is an error, and one Slack line

```gherkin
Given both attempts fail
When Harry pushes
Then it raises, so the caller knows the page did not arrive
And Slack carries one line naming the tablet and what happened, once per 24 hours
And the line contains no token, no URL and nothing from the response body
```

### Scenario 5: The token never appears anywhere

```gherkin
Given DEVICE_TOKEN is set to a value
When the connector logs at DEBUG, raises on a failed push, and alerts
Then that value appears in none of them
```

### Scenario 6: Pairing is one command

```gherkin
Given a machine with no DEVICE_TOKEN
When `make remarkable-pair CODE=abcd1234` is run with a code from my.remarkable.com/device/desktop/connect
Then the code is exchanged once for a device token
And the token is written to .harry/connectors/remarkable/.env.local, which is gitignored
And the command prints that it worked without printing the token
```

### Scenario 7: Claude can put a document on the tablet

```gherkin
Given a session with the remarkable_push_document tool
When Claude calls it with a path to a PDF and a name
Then the PDF is on the tablet under that name
When Claude calls it with markdown text and a name instead
Then the markdown is rendered to a PDF at 509.34 by 679.13 points and pushed
And calling it with neither, or with both, is an error saying which
```

### Scenario 8: Claude can see what is already there

```gherkin
Given three documents in the configured folder
When Claude calls remarkable_list_documents
Then it gets their names, their ids and when each was last modified, newest first
And a folder that does not exist yet is an empty list, not an error
```

### Scenario 9: No token is a connector that is skipped, not broken

```gherkin
Given DEVICE_TOKEN is not set
When Harry starts
Then the remarkable connector is skipped, saying which setting is missing
And both its tools are skipped, saying they need it
And every other capability comes up
```

### Scenario 10: The client is pinned to an exact version

```gherkin
Given remarkapy's protocol is reverse-engineered and a release broke every write in August 2026
When the dependency is declared
Then it is pinned to exactly 0.3.1, with the reason beside the pin
And no Go rmapi binary is required, by Harry or by the container
```

## When it degrades

| What broke | What the caller gets | What reaches Slack |
|---|---|---|
| One upload attempt fails | Nothing — it is retried once and the answer is the second attempt's | Nothing. A retry that worked is not a fault |
| Both attempts fail | An error saying the push did not happen | One line naming the tablet and why, once per 24 hours |
| The token has been revoked | An error saying the tablet refused the token and to re-pair | The same line, naming re-pairing as the fix |
| reMarkable's cloud is down | An error saying it could not be reached | The same |
| No token configured | The connector is not there at all; the digest's `optional:` means the page renders and stays on disk | The loader's own start-up alert, once a day |

**The morning page survives every row of that table.** `digest_build` writes the PDF to disk
first and pushes second, so a failed push costs the delivery and not the page.

## Out of scope

- Reading, deleting, moving or renaming documents on the tablet.
- Annotations, templates, notebooks, and anything that is not a document being added.
- Retrying on a schedule. One retry, inline, then say so. A background retry queue is its own
  feature and needs somewhere to keep the queue.
- Pushing to more than one folder, or to a nested path.
