# Requirements — FEAT-260912-cfeb21 Every unknown that could sink the morning page is settled

## Context & problem

Five things the plan depends on have never been run. Each one, if it fails, changes a
design rather than a detail — and each is cheap to test now and expensive to discover
later, after code has been written on the assumption it works.

One of them has moved onto the critical path since the plan was written. The morning page
is triggered by a Claude scheduled task rather than by Harry, so **whether a Claude
scheduled task can reach a self-hosted MCP server at all decides whether the digest has a
trigger.** Nothing in Phase 1 is safe to build until that is answered, because the answer
changes where the clock lives.

The rest are cheaper but not optional. De Tijd is the source most worth having and the one
most likely to be unreachable. The reMarkable protocol is reverse-engineered and the free
tier's limits are contested by two independent implementers. Apple's Reminders support over
CalDAV is the flakiest dependency anyone lists. And the Slack loop, two phases away, rests
entirely on whether a blocking tool call survives.

## Goals

- Answer each question with something that ran, not something that was read.
- Write each finding where the decision that depends on it will be read.
- Change the plan now, on evidence, rather than after the code exists.

## Non-goals

- Working code. Everything here is thrown away; nothing in `scratch/` is ever imported.
- Handling the failure cases well. A spike proves the happy path is reachable at all.
- Answering the two questions the plan already settled: the CLI on the NUC is gone with the
  decision that Harry never calls a model, and Claude Desktop is the same question as the
  scheduled task from a different client.

## Scenarios

### Scenario 1: A Claude scheduled task reaches Harry

```gherkin
Given a trivial MCP server reachable at https://harry.<domain>/mcp behind a bearer token
And a Claude scheduled task configured to call its ping tool
When the scheduled task fires
Then the tool result comes back to that session
And the plan keeps the trigger on Claude's side
```

If it fails, the clock has to live somewhere that is still not Harry — a cron entry on the
NUC calling the tunnel, or a Claude Code routine — and that is the finding.

### Scenario 2: A De Tijd article comes back in full

```gherkin
Given a De Tijd session logged in by hand in a headed browser and saved with storage_state
When the saved session is reused headless to open one article
Then the article body is on stdout with more than 1,000 characters of prose
And how many days old the session was is recorded
```

This is the riskiest one. If it fails, De Tijd carries RSS summaries only and the full-text
scenarios on that connector are dropped rather than degraded.

### Scenario 3: A blocking tool call survives five minutes

```gherkin
Given an MCP tool that sleeps for five minutes before returning
When a Claude Code session calls it
Then the result arrives and the session continues in the same turn
And the tool timeout setting that governs it is recorded, with its ceiling
```

If it fails, the Slack loop becomes `ask_human` returning a request id plus a `check_answer`
poll — more turns, same outcome, a different module. Phase 4 is not designed until this is
answered.

### Scenario 4: A PDF reaches the tablet

```gherkin
Given a device paired with rmapi using a code from my.remarkable.com
When a one-page PDF is pushed with remarkapy
Then it appears on the tablet
And whether this account's tier carries it is recorded, against the 50-day rule
```

Two independent implementers claim a Connect subscription is required and the documentation
suggests otherwise. Five minutes of testing beats designing around a guess.

### Scenario 5: iCloud answers over CalDAV

```gherkin
Given an app-specific password from appleid.apple.com
When the calendars at https://caldav.icloud.com are listed and today's events fetched
Then today's events come back with time, title and location
And whether Reminders arrive as VTODO is recorded either way
```

If Reminders do not arrive, the to-do section moves source or drops. It does not block
anything else.

## When it degrades

A spike reaches real external services, so a failure has two possible meanings and they must
not be confused. **A spike that fails because the service was down is not a finding** — it
is a spike that has not run yet. Record which one it was, and retry before changing a plan
on the strength of it.

Each spike prints `PASS` or `FAIL` and its evidence on one line. A spike that cannot reach
its service at all prints `UNKNOWN` and why.

## Out of scope

- Retry, logging, alerting, configuration, or any structure at all. These are scripts.
- The Slack loop itself, the digest renderer, and every connector. Those are separate
  features and none may be started on an unanswered question they depend on.
- Committing anything under `scratch/`. Only its README is tracked.
