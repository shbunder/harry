# Requirements — FEAT-260912-334932 Claude can call Harry from any session

## Context & problem

The loader finds capabilities and registers them. Nothing can reach them. This is the
surface Harry exists to offer: the tools Claude calls, over MCP, at `/mcp`.

Harry's entire value crosses this one boundary. Get the shape wrong and correct plumbing
behind it does not help, because the model either cannot find the right tool or cannot tell
what it does. The shape was decided in [[ADR-260912-b22e46]] and is not reopened here —
this feature builds it.

Two things this must get right that are easy to get wrong:

- **The description is the product.** A tool's `TOOL.md` body is what Claude reads to
  decide whether to call it, and small changes to it move selection accuracy more than
  almost anything else in the repo. It is served verbatim. Harry never edits, summarises or
  templates it — that would be reasoning.
- **The roster is sent on every request.** Every tool loaded and unused is rent, paid
  forever. Most tools stay out of it until somebody asks for one.

## Goals

- Every tool a capability registered is callable over MCP, with the description, the
  annotations and the schema its declaration and signature already carry.
- Most tools stay out of the roster until they are searched for.
- A `trigger: claude` job's brief is an MCP prompt, so a scheduled task invokes it rather
  than calling a tool to fetch text.
- A caller with no token or the wrong token gets nothing.
- A tool that wants to know who is asking can find out.

## Non-goals

- **Any actual tool.** This publishes what the loader registered. Weather, iCloud and the
  digest are their own features; the fixtures here stand in for them.
- The scheduler. A job's brief becomes a prompt here; running a job on a timer does not.
- `outputSchema` and `resource_link` beyond what FastMCP derives on its own. Both belong to
  the tools that return large things, and designing them against a fixture that returns
  `{'day': 'today'}` would be designing against nothing.
- OAuth, token issuing, token rotation. One static token resolving to one principal, which
  is the seam that already exists in `harry.config` — and which is explicitly not
  authentication for a second person.
- Rate limiting, quotas, and per-person tool permissions.

## What the protocol will not do for us

**A per-session tool roster is not available.** The plan was that a tool revealed by a
search would be revealed for that session only. `Context.session_id` in FastMCP 4.0.3 is a
fresh value on every request — measured, on the in-memory transport and over real HTTP with
`stateless_http=False`, four requests giving four different ids. Nothing else in the
request identifies a conversation.

So **a reveal is server-wide and lasts until Harry restarts.** That is a disclosure change
and not a permission change: every principal is already allowed every tool, so what one
person's search costs everybody is a few hundred tokens of roster, not access they did not
have. When per-person permissions arrive they will need a stable session, and this is the
line to come back to.

## Scenarios

### Scenario 1: A declared tool is callable, described by its own body

```gherkin
Given a loaded tool capability whose TOOL.md body describes what it returns
When a client lists the tools
Then the tool is there under its declared name
And its description is the body of TOOL.md, verbatim
And its annotations are the ones in the frontmatter
And its input schema is derived from the typed Python signature, not declared anywhere
When the client calls it
Then the function the capability registered runs, and its result comes back
```

### Scenario 2: A capability that did not load is not published

```gherkin
Given a tool whose required setting is absent, so the loader skipped it
When a client lists the tools
Then it is not there
And /health still explains why
```

A skipped tool that still appears in the roster is worse than one that is missing: Claude
picks it, and the failure looks like a bug in the tool rather than a missing credential.

### Scenario 3: The roster comes back in the same order every time

```gherkin
Given several tools
When a client lists the tools twice
Then both answers are in name order, and identical
```

The MCP specification says deterministic ordering improves prompt-cache hit rates.
Filesystem order is not deterministic, and it is what you get by accident.

### Scenario 4: Most tools are absent from the roster until they are searched for

```gherkin
Given a tool declaring always_load: false
When a client lists the tools
Then it is not in the roster
And harry_find_tools is
When the client calls harry_find_tools with a word from that tool's name or description
Then the answer names the tool and says what it does
And a tools/list_changed notification is sent
And the tool is in the roster from then on
And calling it works
```

### Scenario 5: The roster is never empty

```gherkin
Given every declared tool sets always_load: false
When a client lists the tools
Then harry_find_tools is there
```

A roster with nothing in it is a 400 from the API, not a slow path — the search tool needs
something alongside it. `harry_find_tools` is core's own and is always present, so the
all-deferred case that `scripts/check_capabilities.py` rejects at the gate cannot take Harry
down at run time either.

### Scenario 6: A trigger: claude job's brief is a prompt

```gherkin
Given a job with trigger: claude and a brief in its body
When a client lists the prompts
Then a prompt named for the job is there
And rendering it returns the body verbatim
And a trigger: schedule job has no prompt
```

That is what prompts are for in the protocol, so the job appears in any MCP client's prompt
picker and the scheduled task invokes it rather than calling a bespoke tool to fetch text.
A heuristic job's body is documentation; nothing serves it.

### Scenario 7: No token, or the wrong token, gets nothing

```gherkin
Given HARRY_API_TOKEN is set
When a client connects with no Authorization header
Then it is refused
When a client connects with a token that is not the configured one
Then it is refused
When a client connects with the configured token
Then it gets the roster
```

### Scenario 8: A tool can find out who is asking

```gherkin
Given a tool whose signature declares a principal parameter
When it is called with the owner's token
Then it is handed the owner, and `principal` is not in the tool's input schema
```

The parameter is filled in by Harry, not by the caller, which is the only version of this
that is worth anything.

### Scenario 9: A tool that fails says what to try instead

```gherkin
Given a tool whose function raises
When a client calls it
Then the result is an error, not a crashed server
And the message does not contain a traceback or a file path
And every other tool still works
```

## When it degrades

- **No tools at all** — `harry_find_tools` is the roster, and it says there is nothing to
  find. A Harry with no capabilities is a Harry that starts.
- **`HARRY_API_TOKEN` is unset** — nobody is authorised, including the owner. That is the
  safe direction and it is already how `principal_for_token` behaves: an empty configured
  token must never mean "anything matches", because an unconfigured Harry behind a tunnel
  would then serve the internet.
- **A tool raises** — scenario 9. The error is returned, the server keeps serving, and the
  other tools are unaffected.
- **A tool blocks** — not handled here, and the ceiling is real: a client aborts a silent
  call at 300 seconds. The answer, measured in Phase 0, is that progress notifications reset
  it, and the pattern is in `scripts/mcp_probe.py`. It belongs to the first tool that
  blocks rather than to the transport.

Nothing here reaches Slack. A refused token and a failing tool are both answered to the
caller, in the call. Alerting belongs to FEAT-260912-84c828.

## Out of scope

- Anything about *which* tools exist. That is every other feature.
- The tunnel. Reaching Harry from off the machine is FEAT-260913-fdd33f.
- Resources. Harry serves tools and prompts; nothing here needs a resource yet.
