# Requirements — FEAT-260913-007e6f Harry can post to any channel it has been invited to, not just one

## Context & problem

Harry can say that something went wrong, in one channel, to nobody in particular. That was
the right first thing to build and its own page said so: *"one channel, one kind of message.
A second channel is a setting when somebody wants one."* Somebody wants one.

The ask is not really a second channel, though. It is that **Claude should choose where a
message goes, according to what the message is** — a failure to `#harry`, a finished piece of
work to the channel the people who asked for it are in.

That makes it a tool rather than a setting, and exposing a tool is an explicit choice rather
than a consequence of the connector being able to do it. What Harry can reach and what Claude
is offered are two different lists, on purpose.

**And it uncovers a gap.** A tool declares `requires: [slack]`; the loader checks it and
refuses the tool when the connector is missing. Nothing ever hands the connector over. Every
tool in the repository so far has been a fixture returning a dictionary, so nothing had
noticed that `requires:` is half a contract. This is the feature that needs the other half —
see [[ADR-260913-210e08]].

## Goals

- Claude can post a line to any channel the bot is in, choosing the channel per message.
- A tool can use the connector it declared, without importing it.
- Alerts keep going where they already go, with nothing to reconfigure.
- Posting somewhere the bot has not been invited says what to do about it.

## Non-goals

- **Reading anything from Slack.** Still one-way. Inbound is a second credential, an
  inbound surface and an approval model, and none of it is needed here.
- Formatting: blocks, attachments, threads, mentions, emoji reactions. One line of text.
- An allow-list of channels in Harry's configuration. **Slack is already the boundary** —
  the bot can only post where somebody invited it, and answers `not_in_channel` otherwise.
  A second list in Harry would be one more thing to keep in step with reality, and it would
  be wrong the first time somebody invites the bot somewhere.
- Choosing the channel for a message Harry raises itself. Alerts go to the configured
  channel; deciding where a failure belongs is judgement, and Harry does not do judgement.
- Direct messages to a person.

## What a capability gets handed

`context.connectors` is a mapping of name to whatever that connector registered, holding
exactly what `requires:` listed and nothing else. Decided in [[ADR-260913-210e08]], which
also records that it amends the loader's page — that page pinned `Context` at eight fields
and this is the ninth.

A capability still imports `harry.sdk` and nothing else, and still cannot reach a connector
it did not declare.

## Scenarios

### Scenario 1: A tool is handed the connector it asked for

```gherkin
Given a tool declaring `requires: [slack]`
When Harry loads it
Then context.connectors['slack'] is what the slack connector registered
And a connector it did not declare is absent from the mapping
And the tool's module imports harry.sdk and nothing else
```

### Scenario 2: A connector with nothing to hand over is absent, not None

```gherkin
Given a tool requiring a connector that registered nothing
When Harry loads the tool
Then the connector is not in context.connectors
And the tool is skipped with the KeyError as its reason, at start-up
```

Better a skip at start-up, where `/health` names it, than an `AttributeError` on the first
morning.

### Scenario 3: Claude posts to a named channel

```gherkin
Given the Slack bot is in #claude and in #mykate_cowork
When Claude calls slack_post(channel="#claude", text="the weekly reading list is ready")
Then one chat.postMessage carries #claude and that text, and nothing else
And the answer says which channel it went to
```

### Scenario 4: The configured channel stays the default

```gherkin
When slack_post is called with no channel
Then it goes to the channel in CHANNEL
And an alert Harry raises itself still goes there too, with nothing reconfigured
```

### Scenario 5: A channel the bot is not in says what to do

```gherkin
Given the bot has not been invited to #finance
When Claude calls slack_post(channel="#finance", text="…")
Then the error says not_in_channel and names the channel
And it says to invite the bot
And no other tool is affected
```

`chat:write` is not enough on its own and that is the step people skip, so the error has to
say so rather than repeat the code.

### Scenario 6: The tool is deferred, and findable

```gherkin
Given slack_post declares always_load: false
When a client lists the tools
Then slack_post is not in the roster
When harry_find_tools("slack") is called
Then slack_post is found and can then be called
```

Most tools defer. Posting a message is not something every session needs, and the roster is
sent on every request.

## When it degrades

- **No Slack credential** — the connector disables itself, so the tool is skipped with
  `needs slack, which did not load` and never reaches the roster. Harry starts. Claude sees
  no tool rather than a tool that fails.
- **Slack unreachable, or answering an error** — the connector already raises with Slack's
  own code after five seconds, and the tool returns that as an error to the caller. Nothing
  retries.
- **A channel that does not exist** — `channel_not_found`, returned to the caller. Same
  shape as `not_in_channel` and with the same advice attached.
- **The bot token was revoked** — `invalid_auth` reaches the caller. Still nothing watches
  the credential proactively; that hole is named in the alerting page and is not closed here.

Nothing new reaches Slack when Slack is the problem, for the obvious reason.

## Out of scope

- Any other connector exposing a tool. This ships `context.connectors` and the first real
  use of it.
- Rate limiting. Slack's own 429 is returned like any other error.
