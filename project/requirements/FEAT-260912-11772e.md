# Requirements — FEAT-260912-11772e Harry runs jobs on time, and tells you when one never ran

## Context & problem

Two halves, and the second is the one that matters.

**Harry owns the clock for its own heuristic work.** Refresh a cache at 05:00, retry a
failed push, check whether a credential still works. Each is a rule that can be written
down in advance, so Harry can run it.

**Harry does not own the clock for anything that needs judgement.** A Claude scheduled task
fires the morning page, because choosing what goes on it is the whole reason Harry does not
call a model.

That split has one cost, and it is named in `.claude/rules/no-model-calls.md`: **an external
trigger cannot report its own absence.** A scheduled task that never fires produces silence,
and silence looks exactly like a morning you did not check. When Harry owned the trigger, a
morning with no page was a job that failed and said so. Now nothing says anything.

The deadline watchdog is the only thing that can tell those two apart, which is why it is
here and not in a later phase.

## Goals

- A `trigger: schedule` job runs at its cron time, in the timezone it declares.
- A job cannot be started while it is still running.
- A job that fails is logged, alerted, and costs only itself.
- Harry knows when a `trigger: claude` job last finished, across a restart.
- A deadline that passes with nothing finished reaches a person, once.

## Non-goals

- **The morning page.** No digest, no renderer, no tablet. This ships the clock and the
  watchdog; the job that uses them is its own feature.
- Retries and backoff. A job that fails fails; the alert is the answer, not a retry loop.
- Job history, run durations, or anything a dashboard would read. The store keeps one fact
  per job — when it last finished — because that is what the watchdog asks.
- Misfire recovery for a machine that was switched off. If Harry was not running at 05:00
  the job did not run, and the deadline watchdog is what notices anything that mattered.
- Distributed scheduling, or more than one Harry. One machine, one scheduler.
- Pausing, resuming or rescheduling a job from outside. `enabled:` in the declaration is the
  switch, and it takes effect on restart.

## How Harry finds out a Claude-triggered job finished

It cannot know on its own. So the job tells it, and the mechanism lives in the job's own
file rather than in core:

**`harry_job_finished(job)` is a core MCP tool**, always in the roster, and a
`trigger: claude` job's brief ends by telling Claude to call it. The brief is the job's
whole definition and is already served verbatim as an MCP prompt, so the instruction sits
next to the work it belongs to and core stays ignorant of every job by name.

**The cost, stated:** if Claude does the work and never calls the tool, Harry reports a
missed deadline for a morning page that was in fact delivered. That is the right direction
to be wrong in — a false alarm is noticed and fixed, a silent miss is not — and it is why
the brief template says so in the sentence that matters.

## Where the record lives

`harry.store`, which starts here at its smallest useful size: **one JSON file under the data
volume holding, per job, when it last finished and which deadline has already been
reported.** Read once at start-up, rewritten on each change.

Not SQLite. That is machinery for queries nobody has — this is a mapping of at most a
handful of keys, read once and written a few times a day, and a file that a person can
`cat` when they are wondering why the watchdog is quiet is worth more here than an index.
When something needs a query, SQLite arrives with it.

**Durable on purpose.** In memory, a restart would lose every completion and the watchdog
would alert for a morning page that was delivered an hour earlier — a false alarm on every
deploy, which is exactly how a channel gets muted.

## Scenarios

### Scenario 1: A scheduled job runs at its cron time, in its own timezone

```gherkin
Given a job with `schedule: "0 5 * * *"` and `timezone: Europe/Brussels`
When Harry starts
Then that job is scheduled to fire at 05:00 Brussels time
And a job in a different timezone fires at its own 05:00, not Harry's
And what runs is the function the capability registered
```

### Scenario 2: A job already running is not started a second time

```gherkin
Given a scheduled job whose run takes longer than its interval
When its next fire time arrives while it is still running
Then the second run does not start
And the fact that it was skipped is logged
```

A cache refresh that has stopped answering does not want a hundred copies of itself; it
wants one, and somebody told.

### Scenario 3: A job that raises costs only itself

```gherkin
Given two scheduled jobs, one of which raises
When both fire
Then the other one still runs
And the failure is logged with its exception type and message
And one alert names the job and what it raised
And the key is the job, so a job failing every five minutes reports once a day
```

### Scenario 4: Harry remembers that a job finished

```gherkin
Given a trigger: claude job
When harry_job_finished("morning-page") is called
Then the time is recorded under the data volume
And it is still there after Harry restarts
And calling it for a job that does not exist is an error naming the job
```

### Scenario 5: A deadline that passes with nothing finished reaches a person

```gherkin
Given a trigger: claude job with `deadline: "07:00"` and `timezone: Europe/Brussels`
And nothing has finished it since midnight Brussels time
When 07:00 Brussels time arrives
Then one alert is sent: "morning-page has not run today. It was due by 07:00."
And the alert is keyed on the job and the date
```

### Scenario 6: A deadline that passes after the job finished says nothing

```gherkin
Given the same job, finished at 06:45 Brussels time
When 07:00 arrives
Then nothing is sent
And a completion from yesterday does not count as today's
```

"Since midnight in the job's own timezone, on the day the check runs" is the whole rule. A
page built at 23:50 last night is not this morning's page.

### Scenario 7: A missed deadline is reported once, and a restart does not repeat it

```gherkin
Given a deadline was missed and reported at 07:00
When Harry restarts at 07:05 and the check runs again
Then nothing further is sent for that job today
```

The alert layer already suppresses a repeated key for 24 hours, and it does that in memory.
A restart clears that memory, which is fine for a fault that repeats every five minutes and
wrong for one reported once a day — the second report would arrive on every deploy. So the
date already reported is written down beside the completion, in the same file.

### Scenario 8: Nothing to run is a working Harry

```gherkin
Given no jobs on disk
When Harry starts
Then the scheduler starts with nothing in it and says so
And Harry serves
And a job with `enabled: false`, or a trigger: claude job with no deadline, is not watched
```

## When it degrades

- **A job raises** — scenario 3. Logged, alerted, everything else keeps its schedule.
- **A job hangs** — not handled, deliberately. `max_instances` stops a second copy starting,
  so a hung job stops running rather than piling up, and its deadline — if it has one — is
  what notices. A timeout around arbitrary capability code is machinery for a case nobody
  has hit, and the same call was made for the loader's imports.
- **The store cannot be read** — corrupt file, bad permissions. Harry starts with an empty
  record, says so, and the first watchdog check alerts for everything. A false alarm is the
  safe direction; refusing to start because a cache file is unreadable is not.
- **The store cannot be written** — the completion is logged and lost, so the watchdog may
  alert for a job that ran. Logged at WARNING each time, because a data volume that is
  read-only is a real problem somebody should hear about.
- **Slack is down when a deadline is missed** — the alert layer already handles it: the
  message is lost, the failure is logged, and the date is **not** recorded as reported, so
  the next check tries again.
- **Harry was switched off at the cron time** — the job did not run. Nothing pretends
  otherwise. If it mattered it had a deadline, and the deadline is what notices.

## Out of scope

- Any actual job. The fixtures stand in, as they did for the loader.
- A job that needs to run on more than one machine.
- Changing a schedule without restarting.
