# Requirements — FEAT-260912-8a0ab0 Harry starts with whatever is on disk, and one broken capability is skipped

## Context & problem

Everything Harry can do is a folder somebody dropped in. This is the code that finds those
folders, reads them, runs their `register`, and hands them their settings — and it is the
only code in Harry that every capability depends on.

The property that decides whether this design is usable is not discovery. It is what
happens when one of them is broken. **A half-written capability must be logged and stepped
over, not fatal.** Without that, the first thing left unfinished stops the morning page
rendering at all, and the honest response is to stop developing in `.harry/` — which is the
whole product.

That failure is not hypothetical: it is the normal state of a folder somebody is midway
through writing, and it is the state every third-party capability will be in at some point.

Two things already exist and are not in scope to design again. `scripts/check_capabilities.py`
validates declarations at the gate, and `harry.config` resolves a capability's settings
through five layers. This feature is the loader that uses both at run time.

## Goals

- A connector, a tool and a job under `.harry/` all load without core naming any of them.
- One broken capability costs exactly itself.
- Whatever went wrong is visible without reading a log file.
- A capability in a later root replaces an earlier one of the same name.
- The contract a capability is written against is pinned here, because every later feature
  is written against it.

## Non-goals

- The MCP server. Publishing tools over MCP is its own feature; this one registers them.
- The scheduler. Declaring a job is here; running it on a timer is not.
- The store. Nothing here persists anything.
- Entry-point discovery. The roots list already has room for it; there is nothing to
  install yet.
- Hot reload. Harry restarts to pick up a change, as Home Assistant does.
- `route`, `slack_action` and `on`. `CLAUDE.md` names them as the registry's eventual
  surface, and each arrives with the feature that executes it — an HTTP route with the
  first capability that serves one, `slack_action` with FEAT-260912-84c828, `on` with the
  first thing that emits an event. Adding them now would be three methods nothing calls,
  which `.claude/rules/inert-controls.md` names as the sibling defect. **Stating that they
  are deferred is the point**: the next feature adds one deliberately rather than
  discovering a gap.

## Where the fixtures live

**Broken capabilities are test fixtures, not repository contents.** They live under
`tests/fixtures/capabilities/<case>/` and are loaded through a temporary root, because
`scripts/check_capabilities.py` validates everything under `.harry/` and runs in `make lint` —
a deliberately malformed declaration parked there would fail the gate on every run, for
everyone, forever.

`.harry/` stays gate-clean. Every scenario below that says "a capability that is broken"
means one of those fixtures, copied into a `tmp_path` root that `capability_roots()` is
pointed at.

## Scenarios

### Scenario 1: Three kinds load, and core names none of them

```gherkin
Given a connector, a tool and a job in a capability root
When Harry starts
Then all three are registered
And `git grep -n weather -- src/harry/` finds nothing
```

The grep is written that way on purpose: `grep -rn … src/harry/*.py` is the version that
looks right and searches only the top level, so it would stay green with a capability name
sitting in a subpackage.

### Scenario 2: A capability that raises is skipped, and the rest come up

```gherkin
Given a connector whose module raises ImportError at import
And a second connector which is fine
When Harry starts
Then Harry is serving
And the second one is registered
And the broken one is not registered
And the failure is recorded with its exception type and message
```

### Scenario 3: A declaration that does not parse is skipped, not raised

```gherkin
Given a capability whose CONNECTOR.md has unclosed frontmatter
When Harry starts
Then it is skipped with the parse error as its reason
And every other capability still loads
```

`make lint` catches this before it ships. Run time still has to survive one, because a
third party's folder never passed your gate.

### Scenario 4: Missing configuration disables one capability, not Harry

```gherkin
Given a connector declaring `app_password` as required
And no value for it in any of the five layers
When Harry starts
Then it is not registered
And the reason names the setting: "icloud: required setting app_password is not set"
And Harry is serving
```

### Scenario 5: /health says what loaded and what did not

```gherkin
When GET /health is called
Then it returns 200 with each capability, its kind, and loaded or skipped
And every skipped one carries the reason it was skipped
And the response names no secret, in any field
```

A skipped capability is not an error status. Harry running with four of five is Harry
running — the point of the endpoint is that the missing one is visible rather than silent.

"Names no secret" is not a hope about exception messages. Every value the capability
declared `secret: true` is redacted out of any reason before it is recorded, because the
message that goes wrong is exactly the one somebody wrote as
`raise ValueError(f'bad token {token}')`.

### Scenario 6: A later root shadows an earlier one, by name

```gherkin
Given a connector named icloud in an earlier root
And a connector named icloud in a later root
When Harry starts
Then the later one is registered and the earlier one is not
And a WARNING names both paths: "icloud: replaced by <later path>, shadowing <earlier path>"
And /health carries the earlier one as shadowed, naming the root that replaced it
```

Both channels, deliberately. The log line is what somebody watching a restart sees; the
`/health` field is what answers "why is this one behaving differently from the code I am
reading" three weeks later. Silently replacing code is worse than replacing it loudly.

### Scenario 7: An out-of-tree capability loads like any other

```gherkin
Given HARRY_CAPABILITIES_DIR pointing at a directory outside the repository
And a connector inside it
When Harry starts
Then it is registered exactly as one in .harry/ would be
And its settings resolve from its own folder, not from the repository's
```

### Scenario 8: A capability may only import the SDK

```gherkin
Given a capability that imports harry.scheduler
When Harry starts
Then it is skipped with a reason naming the import
And the module is never executed
```

Enforced at run time rather than only in review, because the rule is what keeps core
replaceable and a review catches it only if somebody is looking. The check reads the
module's imports before running it, so a forbidden import never takes effect. It cannot
see `importlib.import_module('harry.scheduler')`, and that is a stated limit rather than
an oversight — the rule is a boundary for people writing capabilities, not a sandbox.

### Scenario 9: The contract a capability is written against

```gherkin
Given a capability folder
When the loader registers it
Then it calls register(registry, context) in connector.py, tool.py or job.py
And registry exposes exactly connector(), tool() and job()
And context carries name, kind, folder, declaration, body, config, config_for() and log
And a folder with no Python at all registers its declaration alone
And harry.sdk imports nothing from harry.loader, harry.main or any capability
```

The last line is what lets a `trigger: claude` job be one markdown file.

`context.config` is resolved with no principal — registration happens once, at start-up,
and is not a call. `context.config_for(principal)` is the seam ADR-260913-f38787 asks for:
a call that knows whose calendar it is re-resolves the same schema for that person.

`registry` is scoped to the capability being loaded, so `registry.tool(fn)` needs no name —
the name, the description, the annotations and `always_load` all come from the declaration
the loader has already read. The declaration is the metadata; the Python is the behaviour,
and neither repeats the other.

## When it degrades

This feature *is* the degradation machinery, so the question is what happens when it is
the thing that breaks.

- **No `.harry/` at all** — Harry starts with no capabilities and says so. A fresh install
  is not an error.
- **A root that does not exist** — skipped. Bundled is empty today and
  `HARRY_CAPABILITIES_DIR` is usually unset.
- **A malformed declaration** — scenario 3.
- **A capability that hangs on import** — not handled, and deliberately not. A timeout
  around every import is machinery for a case nobody has hit; if it happens, `/health`
  never answers and that is a visible failure rather than a silent one.

Nothing here reaches Slack. Alerting belongs to **FEAT-260912-84c828** ("Harry can tell you
something went wrong"), which inherits this case: a capability skipped three weeks ago looks
exactly like one that was never installed, and only an alert tells the difference. A
start-up failure is visible in `/health` and in the logs on the machine somebody just
restarted, which is enough until that feature lands.

## Out of scope

- Any capability. This feature ships the loader and its test fixtures, not weather or iCloud.
- Restarting or reloading a capability while Harry runs.
- Dependency ordering between capabilities. `requires:` is a declaration the loader checks,
  not a graph it sorts.
