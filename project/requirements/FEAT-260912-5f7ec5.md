# Requirements — FEAT-260912-5f7ec5 The page knows what the weather will do in Leuven

## Context & problem

The smallest source, and the one that proves the shape. Open-Meteo needs no key and answers
today in a single call, so the connector contract gets exercised end to end before anything
with a credential depends on it.

It is also the first thing you can ask Harry for from a Claude session and get a real answer
to. Everything so far has been machinery: a loader with nothing to load, a tool surface with
one tool that posts to Slack, a scheduler with nothing to run. This is the first time Harry
knows something.

It has one interface to satisfy, written down by the page that will call it:
`weather.today()` returns `{summary, high, low, rain_chance}`, or `None` when it has nothing.
See [[FEAT-260912-0f2744]].

## Goals

- Today's forecast for Leuven, from one call, with no account and no key.
- Claude can ask for it from any session.
- Open-Meteo being down costs the weather line, and nothing else.
- Somewhere other than Leuven is a setting, not a code change.

## Non-goals

- **Tomorrow, or the week.** The page is a morning page. A forecast for a day that is not
  today is a different question and nobody has asked it.
- Hourly detail, wind, pressure, sunrise. The page has one line for this.
- Caching. One call a morning against a free endpoint that answers in milliseconds.
- Retries. One attempt; the section says unavailable and the page renders.
- Geocoding a place name. Coordinates are a setting, and looking them up once by hand beats
  a second network call every morning.

## A source being down is an answer, not an error

Two callers, two right behaviours, and the difference matters:

- **`weather.today()`**, which the digest calls, returns `None`. The page prints "Weather
  unavailable" and the rest renders.
- **`weather_forecast`**, the tool Claude calls, returns `{available: false, why: …}` rather
  than raising. A tool that raises tells the model it did something wrong, and it did not —
  the answer to "what is the weather" when the service is down is "nobody knows", which is
  information.

`tool-design.md` asks an error to steer — "no articles since 05:00, try since=yesterday".
There is nothing to steer to here. Trying again in a minute is not advice worth the round
trip, and inventing some is the kind of helpfulness that makes a model retry forever.

## Scenarios

### Scenario 1: Today's forecast, from one call

```gherkin
Given latitude 50.88 and longitude 4.70, which is Leuven
When the connector is asked for today
Then one GET reaches api.open-meteo.com carrying those coordinates and the timezone
And the answer is {summary, high, low, rain_chance}
And high and low are whole degrees Celsius, and rain_chance is a whole percentage
```

Rounded because the page is read at arm's length over coffee. "9–17°, cloudy, 20% rain" is
the line; `16.8` and `19.4%` are noise on paper.

### Scenario 2: Claude can ask for it

```gherkin
When Claude calls weather_forecast()
Then it gets the same four facts, and the place they are for
And the tool is deferred, so it is found with harry_find_tools rather than sitting in the
  roster every request
```

### Scenario 3: Open-Meteo not answering costs the weather line

```gherkin
Given Open-Meteo refuses the connection, answers 500, or does not answer within 5 seconds
When the connector is asked for today
Then it returns None
And the tool answers {available: false, why: "..."} rather than raising
And nothing else on the page is affected
```

**Five seconds**, because the digest's build is already the call that blocks and a hanging
weather lookup adds to it directly.

### Scenario 4: An answer that is not the shape it should be

```gherkin
Given Open-Meteo answers 200 with a body that is missing today's entry
When the connector is asked for today
Then it returns None and says so in the log
```

A free endpoint changing its shape is a thing that happens, and the failure it must not
produce is a `KeyError` in the middle of building a page.

### Scenario 5: Somewhere else is a setting

```gherkin
Given latitude, longitude, timezone and place in the connector's own .env.local
When the connector is asked for today
Then the call carries those coordinates and the tool's answer names that place
```

Defaults are Leuven — 50.88, 4.70, Europe/Brussels — because that is where the page is
read, and a default nobody has to set is one fewer thing between a fresh clone and a
working page.

### Scenario 6: Every test runs against a recorded answer

```gherkin
When the suite runs
Then no test reaches api.open-meteo.com
And the happy path, the 500, the timeout and the malformed body are all recorded fixtures
```

A suite that reaches the network is a suite that fails on a train.

## When it degrades

- **Open-Meteo unreachable, slow, or answering an error** — scenario 3. One attempt, five
  seconds, the section says unavailable, the page renders.
- **The answer is not the shape it should be** — scenario 4. Same outcome, logged.
- **Coordinates that are not a place** — Open-Meteo answers for whatever point it is given;
  the sea has weather. Nothing validates this, and nothing can.

**Nothing reaches Slack.** There is no credential to lapse — the case alerts exist for — and
a morning where the weather line says unavailable is visible on the page itself, every
morning, to the person holding it. An alert from here would fire on every blip of a free
endpoint, which is how a channel gets muted.

## Out of scope

- Any other source, and the page itself.
- A second location on one page.
