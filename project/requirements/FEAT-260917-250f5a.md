# Requirements — FEAT-260917-250f5a Harry's browser runs in its own container, with no credential to steal

## Context & problem

De Tijd is read in a headed Chromium, and that browser renders whatever De Tijd's pages carry —
their advertising and tracking scripts included. Today it runs **as root, without Chromium's
sandbox, inside Harry's own container**, which since 2026-09-17 can read every credential Harry
holds: each connector's `.env.local` through the `/settings` mount (the tablet token with no
scopes, the iCloud app password, the Slack token, the De Tijd password), the root `.env.local`
with the MCP bearer token, and the saved De Tijd session on `/data`.

One exploit in the renderer reaches all of them. The owner accepted that on 2026-09-17 to get
De Tijd running, on condition this followed — see [[ADR-260916-b26785]].

Measured on 2026-09-17, from `harry:6220e5c` on this NUC, with the browsers reinstalled to a
shared path so a non-root user can read them:

| What was tried | What happened |
|---|---|
| Non-root (uid 1000), no sandbox | Chromium starts, De Tijd answers **200** |
| Non-root, `chromium_sandbox=True`, Docker's default seccomp | **Will not launch**: `TargetClosedError` |
| The same with `--security-opt seccomp=unconfined` | Starts sandboxed, De Tijd **200** |
| The same with `--cap-add SYS_ADMIN` | Starts sandboxed, De Tijd **200** |
| The same with `--security-opt systempaths=unconfined` | Still will not launch |
| The maintained-by-nobody `chrome.json` seccomp profile from jfrazelle/dotfiles | **The container will not start at all** under runc 29.1.3 — it predates syscalls the runtime now needs |
| `playwright run-server` in one container, `chromium.connect()` from another | Works. Headed and sandboxed when the launch options are in the connect URL, De Tijd **200**, `storage_state()` returns the cookies to the caller, and the caller's container has no `/settings` |
| The same without launch options in the URL | The server launches **headless**, and De Tijd answers **403** |

Two lessons decide the design. **The sandbox needs Docker's seccomp filtering relaxed**, and no
maintained profile is at hand — so whatever runs sandboxed should be a container worth little.
And **a browser in its own container can do everything Harry needs**, which removes the prize
rather than raising the wall.

## Goals

- The browser that renders De Tijd's pages holds **no credential**: not the mounted `.env.local`
  files, not the root `.env.local`, not the saved session on disk. Harry hands it the session for
  the call and keeps the file; the container has no volume, so whatever the browser writes dies
  with it.
- Reaching that browser has a number, like every other wait De Tijd's connector makes, and the
  hard limit on a read is the sum that includes it.
- That browser runs **as a non-root user with Chromium's sandbox on**.
- De Tijd still reads exactly as it does today: headed, 200, whole articles, session renewed.
- A machine with no browser container — a laptop, `make serve`, the live tests — still works.
- What the browser container is, and what it is deliberately not given, is written down where
  an operator looks.

## Non-goals

- **Harry's own container running as a non-root user.** Worth doing, and a different risk: with
  the browser gone from it, nothing in Harry's container renders hostile content. It needs the
  `harry-data` volume's ownership migrated, which is its own feature.
- **A vendored seccomp profile.** Measured dead on this runtime, and a 36 KB third-party JSON
  nobody here maintains is a dependency that rots quietly.
- **Blocking the third-party requests a De Tijd page makes.** De Tijd's bot filter judges what a
  browser looks like, and a blocked request list is a way to be refused. Not while it answers 200.
- **A browser for the dev stack.** Dev has no De Tijd credentials, so it never opens a browser.
- **Changing what De Tijd's connector decides.** The rules, the waits and the sentences are
  untouched; only where the browser runs changes.

## Scenarios

### Scenario 1: The browser container holds nothing worth stealing

```gherkin
Given the real stack is running
When the browser container is inspected
Then it mounts no .harry/, no root .env.local and no data volume
And it is handed no environment variable holding a credential
And nothing in it can read /settings, because there is no /settings
```

### Scenario 2: It runs unprivileged and sandboxed

```gherkin
Given the browser container is running
When a page is opened through it
Then the process that opened it is not root
And no Chromium process in that container carries --no-sandbox, so the sandbox is on rather than asked for
And the container drops every Linux capability, may gain no privileges, and keeps nothing it writes
And it is the only container here with its syscall filtering relaxed — neither Harry stack has it
```

### Scenario 3: De Tijd reads exactly as before

```gherkin
Given the tijd connector is pointed at the browser container
When a De Tijd article is asked for through news_article
Then the page is opened headed, and De Tijd answers 200
And the whole article comes back — more than 1,000 characters where a reader who is not logged in gets 263
And the session saved on Harry's data volume is the one used and renewed
```

### Scenario 4: Headed is not an accident

```gherkin
Given a browser container and a connect that names no launch options
When a De Tijd page is opened through it
Then the browser is headless and De Tijd answers 403
And so every connect Harry makes names all three: headed, full Chromium, sandbox on
```

### Scenario 5: No browser container is not a broken Harry

```gherkin
Given a machine with no browser container — a laptop, or `make serve`
When the tijd connector has no endpoint configured
Then it starts a browser of its own, as it does today
And the live tests, which do exactly that, still pass
```

### Scenario 6: A browser container that is down costs De Tijd only

```gherkin
Given the browser container is stopped
When a De Tijd article is asked for
Then the article answers available: false with the feed's summary
And one Slack line says the browser could not start
And VRT NWS and BBC News articles are fetched and returned as before
```

## When it degrades

| What happened | What the page shows | What reaches Slack |
|---|---|---|
| The browser container is down, or unreachable on the network | De Tijd stories print their summary | The existing `browser` line, once per 24 hours |
| The browser container is up but refuses the launch options | The same | The same line |
| Harry's image and the browser's disagree on the Playwright version | The same | The same line. Both come from one image, so this only happens mid-deploy, between one container restarting and the other |
| Chromium's sandbox cannot start in the browser container | Nothing is read, and the line says the browser could not start | The existing `browser` line — a failure that is loud rather than a silent fall back to no sandbox |
| The browser container accepts the connection and then stalls | The summary, once the read's 150-second limit gives up on it | The existing `stuck` line, which names the article rather than the browser. Its runbook row says to restart the browser container when it repeats |
| Nothing sets the endpoint on a stack that has credentials | De Tijd reads normally — **and that is the danger**: Harry starts a root, unsandboxed browser beside the credentials, and nothing on the page or in Slack differs | Nothing. Only the compose test that asserts the real stack names the browser stands between here and there |

**No silent fallback.** A browser container that will not give a sandboxed browser is a failure
Harry reports; it never quietly launches an unsandboxed one instead.

## Out of scope

- Harry's own container's user, and the `harry-data` ownership migration.
- Any change to the De Tijd rules, waits, sentences or fixtures.
- Publishing the browser container's port outside the machine. It is reachable only on the
  compose network, by name.
- A second browser for anything else. When a second site needs one, it uses this container.

## Open questions

- None. The seven measurements in the table above settled them.
