# Requirements — FEAT-260914-fc1515 A capability can report its own failure, not just receive somebody else's

## Context & problem

Alerting is half-built and the missing half is the one that matters.

A capability can offer itself as somewhere alerts go — `registry.alerts(fn)`, which the Slack
connector uses. Nothing lets a capability **raise** one. So the connector that knows its
credential has lapsed cannot say so, which is the exact thing alerting exists for.

Core covers one case on a capability's behalf: one that failed to **load**. That catches "the
Slack token is missing" at start-up and nothing after it. It does not catch the feed that
started 404ing in March, the browser session that expired on Tuesday, or the tablet that
refused two pushes in a row — each a capability that loaded perfectly and then stopped
working.

Found while planning the weather connector, which is the one source that does **not** need
it: no credential, and "Weather unavailable" where a forecast belongs looks like nothing else
on the page. Four features do need it, and three already carry the criterion — De Tijd, whose
whole point is that alert; iCloud; and the tablet. The fourth is news, where a dead VRT feed
just means fewer headlines, which looks exactly like a slow news day.

Decided in [[ADR-260914-c469a4]], including the option that needed no contract change at all.

## Goals

- A capability can say that something went wrong, from its own code, at call time.
- It reports once a day like everything else, without having to think about collisions.
- Reporting never breaks the code that was trying to report.
- A capability with nothing registered to receive alerts still works.

## Non-goals

- **Severities.** One kind of message, as the alerting feature decided. A capability that
  wants to say "this is worse" says so in the sentence.
- Alerting on a capability's behalf by watching its logs. That is the rejected option in the
  ADR, and the reason is in there.
- Anything a capability receives. This is outbound only.
- Retrying, batching or queuing an alert that could not be delivered. The alert layer
  already decides that, and it decides not to.

## Scenarios

### Scenario 1: A capability says something went wrong

```gherkin
Given a connector that has loaded
When its code calls context.alert("the feed has stopped answering")
Then every registered sink is called with that message
And the message is exactly what the capability wrote
```

### Scenario 2: A repeating fault reports once a day

```gherkin
Given a capability alerting with key="feed-down"
When it alerts again four hours later with the same key
Then nothing is sent
When it alerts 24 hours after the first
Then it is sent
And an alert with no key is sent every time
```

The same rule the rest of alerting already uses, reached through the same path rather than
reimplemented.

### Scenario 3: One capability cannot silence another

```gherkin
Given two capabilities both alerting with key="down"
When the first alerts and then the second alerts
Then both are sent
```

**Core namespaces the key**, to `<kind>:<name>:<key>`. A capability passes whatever is
meaningful to it and never has to think about what anybody else might have picked — which is
the only version of this that stays true at thirty capabilities.

### Scenario 4: Nothing registered is still a working Harry

```gherkin
Given no capability registered as an alert sink
When a capability alerts
Then it is a WARNING in the log, naming the capability
And nothing raises
```

### Scenario 5: Reporting never breaks the reporter

```gherkin
Given every sink raises
When a capability alerts
Then the call returns and the capability carries on
And the failure to deliver is logged
```

The code trying to report a problem must not be taken down by the reporting. That promise
already holds in the other direction and now holds in both.

### Scenario 6: An alert raised before the sinks are known

```gherkin
Given a capability that alerts inside its own register()
When Harry starts
Then it is a WARNING in the log
And the capability still loads
And a sink loaded later in the same start-up does not receive it
And the key is not recorded, so the same fault reported at call time is still sent
```

A sink is itself a capability and has to load before it can carry news, so an alert raised
during loading has nowhere to go yet. Rare — nearly every capability alert happens at call
time, hours later — and it is the same behaviour as a Harry with no Slack configured, which
is a working Harry.

**The last line is the one that matters, and it is not the same case.** Alerting already
treats "no sinks configured" as delivered: the log line *is* the delivery, so a keyed fault
in a Harry with no Slack is logged once a day rather than every five minutes. Reusing that
for "the sinks have not loaded yet" would record the key against nobody — and then the same
fault at 06:30, the one message this feature exists to send, would be held back for 24
hours. So `Alerts` knows the difference between *attached with nothing* and *not attached
yet*, and only the first counts as delivery.

### Scenario 7: A secret in the message is scrubbed before it leaves

```gherkin
Given a connector declaring api_key as secret, with a value configured
When it alerts with that value in the message
Then every sink receives the message with [redacted] in its place
```

`Context.redact` already does this for the reason it says: the message that goes wrong is
never the one somebody was careful with, it is `f'the service rejected {token}'` written in
a hurry. A log line stays on the machine. **An alert goes to Slack**, so this path needs it
more than the one it was built for.

### Scenario 8: A capability still cannot reach past the SDK

```gherkin
Given a capability importing harry.alerts
When Harry starts
Then it is skipped with a reason naming the import
```

`context.alert` is the only way in, which is what keeps the sink list core's business.

## When it degrades

- **No sinks** — scenario 4. Logged, nothing raises.
- **Every sink fails** — scenario 5. Logged, the caller carries on, and the key is not
  recorded, so the next occurrence tries again. That last part is the alert layer's existing
  behaviour and is what stops a fault going unheard because Slack was down.
- **A capability alerts repeatedly between calls** — the key is what stops it, and one that
  passes no key gets what it asked for. Nothing rate-limits beyond the daily key, because a
  cap that silently drops alerts is the failure this whole area is about.
- **A sink alerts from its own failure path** — the Slack connector is a sink, and if it
  reported its own failure through `context.alert` it would recurse: send, deliver, sink,
  alert, send. The key cannot stop it, because the key is only written after delivery
  returns. So `Alerts` refuses to re-enter while it is already sending: the inner alert is
  logged and dropped. **A sink should not alert about itself** — the thing that carries the
  news cannot carry news about itself — and this is the guard rather than the rule.

**Nothing new reaches Slack about this feature itself.** It is the path, not a source.

## Out of scope

- Any capability actually using it. News, De Tijd, iCloud and the tablet each add their own
  call, with their own criterion.
- Changing what a sink receives.
