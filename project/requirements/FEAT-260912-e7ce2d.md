# Requirements — FEAT-260912-e7ce2d The page knows what today looks like

## Context & problem

The line on the morning page that says what the day holds. `09:30 standup · 14:00 dentist`,
read over coffee, before you have opened anything.

It comes from iCloud over CalDAV — the protocol Apple exposes for calendars, and the least
reliable surface they have. Two things were settled by a spike on 13 September 2026, and
both changed what this feature is:

- **The connection works.** An app-specific password authenticated against
  `https://caldav.icloud.com` and listed 17 calendars. No surprise there, and it is the
  half that was in doubt.
- **Reminders are not readable, at all.** 14 VTODO items came back across 17 lists and
  **every single one was an Apple upgrade placeholder** — *"De maker van deze lijst heeft
  deze herinneringen bijgewerkt"*, *"Waar zijn mijn herinneringen?"*. Zero real reminders.
  Those lists have been upgraded to a format CalDAV does not expose, and no amount of
  client work reaches them.
- **Recurring events come back wrong.** A search for today with `expand=True` returned an
  event whose `DTSTART` is 2026-09-07 — the series start, not today's instance. Apple
  accepts the expand request and ignores it. An agenda built on that prints last Monday's
  times, or drops the event entirely when the date is filtered.

That third one is the work. A weekly standup is the most common thing on anybody's
calendar, and it is exactly the case that arrives wrong.

**The to-do half of this feature is being dropped**, and the evidence is above rather than
in somebody's memory. See [[ADR-260914-1d19b8]].

## Goals

- Today's events come back with their time, their title and where they are.
- A recurring event shows *today's* instance, at today's time.
- An all-day event says so rather than showing a time nobody set.
- Which calendars are read is configurable, and leaving it empty means all of them.
- iCloud being unreachable costs the agenda line and nothing else, and reaches Slack.
- The app-specific password reaches no log, no error message and no Slack message.

## Non-goals

- **Reminders and to-dos.** CalDAV cannot see them. [[ADR-260914-1d19b8]].
- **Writing anything.** No creating, moving or deleting events. Harry reads.
- Invitations, attendees, free/busy, or responding to anything.
- More than one account.
- Any day but the one asked for. This is not a calendar browser.

## What this offers the digest

The signature FEAT-260912-0f2744 wrote down before this connector existed:

| The digest calls | It gets back |
|---|---|
| `calendar.today()` | `[{at, title, where}]`, in time order — an empty list when there is nothing on |

`at` is `"09:30"` for a timed event and `"all day"` for one without a time. An empty list is
a free day, which is information; it is not the same as iCloud being down, and the digest
can tell them apart because a source that is down raises.

## Where the credential lives

`.harry/connectors/icloud/.env.local`, gitignored, two keys:

```bash
cat > .harry/connectors/icloud/.env.local <<'ENV'
USERNAME=you@icloud.com
APP_PASSWORD=abcd-efgh-ijkl-mnop
ENV
```

The password comes from **account.apple.com → Sign-In and Security → App-Specific
Passwords**, is shown once, and needs two-factor turned on. It is declared `secret: true`,
so `context.redact()` scrubs it out of any alert this connector raises, and
`expires: manual` because changing the Apple ID password revokes every one of them at once.

A container injects `HARRY_ICLOUD_USERNAME` and `HARRY_ICLOUD_APP_PASSWORD`.

## Scenarios

### Scenario 1: Today's events, in order

```gherkin
Given a calendar with a 09:30 standup in a meeting room and a 14:00 dentist appointment
When Harry reads today
Then it returns [{at: "09:30", title: "standup", where: "meeting room"}, {at: "14:00", title: "dentist", where: ""}]
And they are in time order, earliest first
```

### Scenario 2: A recurring event shows today's instance

```gherkin
Given a weekly standup whose series starts 2026-09-07 at 09:30 and recurs every Monday
When Harry reads Monday 2026-09-14
Then the event comes back at 09:30 on 2026-09-14, not on 2026-09-07
```

This is the one iCloud gets wrong on its own. It accepts `expand=True` and returns the
series start, measured against a real account.

### Scenario 3: A moved instance keeps the time it was moved to

```gherkin
Given a weekly standup whose 2026-09-14 instance was moved to 11:00
When Harry reads 2026-09-14
Then it comes back at 11:00, once — not at 09:30, and not twice
```

### Scenario 4: A cancelled instance is not on the page

```gherkin
Given a weekly standup whose 2026-09-14 instance was deleted
When Harry reads 2026-09-14
Then that day's agenda does not contain it
```

### Scenario 5: An all-day event says so

```gherkin
Given an all-day event titled "Shaun on leave", which carries a date and no time
When Harry reads that day
Then it comes back as {at: "all day", title: "Shaun on leave", where: ""}
And it sorts before every timed event that day
```

### Scenario 6: Times are local, not UTC

```gherkin
Given an event stored as 2026-09-14T07:30:00Z
When Harry reads it with TIMEZONE Europe/Brussels
Then `at` is "09:30", because that is the time it is in the room
```

### Scenario 7: A free day is an empty list, not an error

```gherkin
Given nothing on the calendar today
When Harry reads today
Then it returns an empty list
And the page prints "Nothing on today" rather than "Agenda unavailable"
```

### Scenario 8: Which calendars are read is a setting

```gherkin
Given the account has 17 calendars and CALENDARS is "Home, Work"
When Harry reads today
Then only events from those two calendars come back
And a name in CALENDARS that matches no calendar is logged and skipped, and the rest still load
When CALENDARS is empty
Then every calendar in the account is read
```

### Scenario 9: iCloud being down costs the agenda and reaches Slack

```gherkin
Given caldav.icloud.com does not answer within 15 seconds
When Harry reads today
Then it raises, so the page prints "Agenda unavailable" and the rest renders
And Slack carries one line naming iCloud and what happened, once per 24 hours
And the line contains no password, no URL and nothing from the response
```

### Scenario 10: A revoked password says what to do

```gherkin
Given the app-specific password has been revoked, so iCloud answers 401
When Harry reads today
Then the message says the password was refused and to make a new one at account.apple.com
And Slack carries that same sentence
```

### Scenario 11: No credential is a connector that is skipped, not broken

```gherkin
Given USERNAME and APP_PASSWORD are not set
When Harry starts
Then the icloud connector is skipped, saying which settings are missing
And its tool is skipped, saying it needs the connector
And every other capability comes up
```

### Scenario 12: Claude can ask what a day looks like

```gherkin
Given a session with the icloud_list_events tool
When Claude calls it with no arguments
Then it gets today's events
When Claude calls it with day "2026-09-15"
Then it gets that day's events
And a day that is not a date is an error saying the format wanted
```

### Scenario 13: Every parsing test runs against a fixture, never an account

```gherkin
Given iCalendar documents in tests/fixtures/icloud/
When the suite runs
Then no test reaches caldav.icloud.com
And the one that does is marked live and never part of the gate
```

**These fixtures are written by hand, and that is unusual here.** Every other fixture
directory in this repository holds recordings. Nothing could be recorded from a real account
because none was configured when this was built. It is acceptable only because iCalendar is
a specification — RFC 5545 says exactly what `RRULE`, `EXDATE` and `RECURRENCE-ID` mean, so
a document that follows it is not a guess about anybody's behaviour. What they cannot prove
is what iCloud actually sends, which is what the spike measured and what the live test
re-checks. The fixtures' README says all of this, next to the files.

## When it degrades

| What broke | What the page gets | What reaches Slack |
|---|---|---|
| iCloud unreachable or slow | `Agenda unavailable`; everything else renders | One line naming iCloud and why, once per 24 hours |
| The app password was revoked | The same, with a different reason | One line saying to make a new one at account.apple.com |
| One calendar in `CALENDARS` does not exist | The other calendars' events | Nothing — a typo in a setting is a log line |
| One event cannot be parsed | The other events, and that one skipped | Nothing. One malformed entry is not an outage |
| Nothing on today | An empty list, and `Nothing on today` | Nothing. A free day is not a fault |

**An empty agenda and a dead agenda must not look alike.** A free day returns a list; a
source that is down raises. That distinction is the reason this connector raises at all,
since every other read path in Harry answers with `available: false`.

## Out of scope

- Reminders, to-dos and anything VTODO. Dropped with evidence.
- Writing to the calendar.
- Attendees, invitations, free/busy lookups, or travel time.
- Anything past the single day being asked about.
- A second account, or a shared calendar somebody else owns.
