# Requirements — FEAT-260913-fdd33f A Claude scheduled task can reach Harry on the NUC

**Written to be picked up by a session with no memory of the one that wrote it.** Every
fact below was measured on the NUC on 2026-09-15 or -16, and each row says where.

## Context & problem

The morning page needs something to fire it at 06:30. Harry never calls a model, so that
something is Claude, outside Harry. **The operator chose a Claude cloud routine reaching
Harry through a Cloudflare tunnel** — [[ADR-260916-7d4bd0]], which also records the trade
that makes this worth an ADR: a public hostname in front of a service holding a tablet token
with no scopes.

It is not the only route, and the other is proven. On 2026-09-16 a headless `claude -p` on
the NUC called `digest_list_candidates` on the containerised Harry over localhost with bearer
auth and got the real answer back in 8.6s. If a cloud routine cannot be made to reach Harry,
the trigger moves there and the tunnel is deleted.

**What is not known — the reason this starts as a spike:**

- **Whether a cloud routine can present a bearer token to a remote MCP server.** Routines
  read MCP servers from a committed `.mcp.json` or from claude.ai connectors. The docs say
  nothing about a secret in an MCP header, and say of routine environment variables that
  *"anyone who uses the environment can read the values"*.
- **The idle ceiling on a tool call from a cloud routine.** Undocumented — GitHub issues
  suggest ~60s; the CLI measured 300s here; and Cloudflare's edge has its own
  origin-response timeout, 100s by default (error 524). Three different limits on one path.

## Goals

- A Claude cloud routine calls a tool on Harry through `https://harry.marcel-bot.com/mcp`,
  and the result comes back to that routine.
- The route is proven against the **probe**, holding no credential, before Harry is
  reachable on it.
- **Marcel's tunnel is not reconfigured, and nothing in this feature restarts it except
  the deliberate reboot in Scenario 6** — after which it is checked as carefully as before.
- The bearer token is never committed, and the setup nobody will remember is written down.

## Non-goals

- The 06:30 routine's brief and schedule — FEAT-260912-0f2744 builds that on this.
- Reaching Harry from a laptop or phone. Possible once this exists; not built here.
- OAuth, Cloudflare Access, or any auth beyond the bearer token Harry already enforces.
- `HARRY_PUBLIC_URL`. It is documented as the off-machine address, and **nothing reads it**
  — the routine's URL lives in `.mcp.json`. This feature does not set it, and corrects
  `docs/mcp.md`, which currently tells a reader it is how Harry is reached off the machine.

## The decision this feature turns on

**A second named tunnel on the same account, running exactly the way marcel's does.**
[[ADR-260916-7d4bd0]] has the argument. Three rules follow from it, and each is a
criterion:

1. **`--url`, never a config file.** `cloudflared` searches five directories for
   `config.yml` or `config.yaml` by default, and marcel's `--url` process would read one on
   its next start — and `cloudflared` refuses `--url` alongside ingress rules. Harry's tunnel
   writes nothing into any of them except the credentials file `tunnel create` makes, and
   all five are checked before the tunnel runs and again before the reboot.
2. **The probe first, on port 7440, with a throwaway token EXPORTED into the environment —
   and its fingerprint checked before anything is exposed.** The environment outranks
   `.env.local`, but only if the variable reaches the process: an unexported assignment
   does not, and the probe then serves the real token while every other check still passes.
   The banner's fingerprint is compared with the throwaway's before `tunnel run`.
3. **A tunnel that does not end up carrying Harry is deleted**, DNS record included.

## Scenarios

### Scenario 1: A second tunnel, marcel undisturbed

`make doctor` in marcel was the first idea and does not run today; its webhook line also
only reads Telegram's record, which stays healthy until the next delivery. A request that
goes through marcel's tunnel is the check that means something.

```gherkin
Given marcel's tunnel serving marcel-bot.com
And recorded: cloudflared-marcel's ActiveEnterTimestamp, `cloudflared tunnel info marcel` showing connections, and `curl https://marcel-bot.com/health` answering 200
When `cloudflared tunnel create harry` and `cloudflared tunnel route dns harry harry.marcel-bot.com` are run
Then a tunnel named harry exists and harry.marcel-bot.com resolves to it
And neither config.yml nor config.yaml exists in ~/.cloudflared, ~/.cloudflare-warp, ~/cloudflare-warp, /etc/cloudflared or /usr/local/etc/cloudflared
And marcel's ActiveEnterTimestamp is unchanged, its tunnel still has connections, and https://marcel-bot.com/health still answers 200
```

### Scenario 2: The probe answers through the tunnel, and refuses a stranger

```gherkin
Given a throwaway token generated with `export HARRY_API_TOKEN=$(openssl rand -hex 32)`
And the probe started in that shell with `make probe ARGS="serve --port 7440"`
When its banner's fingerprint is compared with `printf %s "$HARRY_API_TOKEN" | sha256sum | cut -c1-12`
Then they match — and if they do not, nothing is exposed and the step stops
When `cloudflared tunnel run --url http://localhost:7440 harry` is started
And `make probe ARGS="call --ping --url https://harry.marcel-bot.com/mcp"` is run from the same shell
Then ping returns
When a request is sent with no Authorization header at all, and another with a wrong token
Then both are refused with 401
And both refused requests appear in the probe's server output with their status
```

**"No token" means no header.** `call --token ''` sends an empty `Bearer ` header, which is
a different request; use `curl` without `-H Authorization`. Send it to `/mcp` with no trailing slash: `/mcp/`
answers 307 before authentication runs, which is neither a refusal nor a pass.

**The client takes the token the same way the server does**, so `call` has to run in the
shell that exported the throwaway. Run from any other shell it sends the real token from
`.env.local` through Cloudflare, and gets a 401 that looks like a successful refusal test.

The last line matters for Scenario 3: it establishes that a refused request is visible at
the probe, which is how "never reached" is told apart from "reached and refused".

### Scenario 3: A cloud routine reaches the probe with a token of its own

```gherkin
Given the probe behind the tunnel with the throwaway token
And `.mcp.json` carrying harry-remote at https://harry.marcel-bot.com/mcp with header `Bearer ${HARRY_API_TOKEN}` and NO fallback, committed on a branch `spike/harry-remote` and pushed to origin
And the routine set to check out `spike/harry-remote`
And the routine's cloud environment allowing outbound HTTPS to harry.marcel-bot.com
When the routine is run with no HARRY_API_TOKEN in its environment
Then its request appears in the probe's server output refused with 401, and the call log shows no successful call
When the same routine is run with the throwaway token in its environment
Then ping returns to the routine's session, and the probe's call log records it
```

**This scenario exists to answer one question, so it has to be able to answer "no".** The
existing `harry` entry falls back to `probe-token-not-a-secret`, and a probe with no token
configured accepts exactly that — a routine holding no secret at all would get `ping` back.
The `harry-remote` entry has no fallback, the probe's token is not the fallback, and the
routine is watched being refused before it is watched succeeding.

**And "no" has to be a real no before it deletes anything.** A request that never appears
in the probe's server output did not reach the probe — the branch, the environment's network
setting, or the routine itself — and is fixed and retried, not recorded as the route failing.
Only a token that **demonstrably does not reach the header** counts as the route not
working. A 401 alone does not prove that: the probe logs the status, not the token, so a
routine still holding an old throwaway also arrives and is refused. **The same probe
session and the same throwaway carry through Scenarios 2, 3 and 4** — restart the probe
between them and every call after is a setup slip that looks like a verdict. And `call`
runs in the shell that exported the throwaway in Scenario 4's NUC-side sleeps too, not only
in Scenario 2.

**Why a branch, not `main`.** Once `harry-remote` is committed where local sessions load it,
any session on a machine that exported the real token — as `docs/mcp.md` tells an operator
to — sends that real token through Cloudflare to a probe holding a throwaway. It lands on
`main` in Scenario 5, when the server behind it is Harry and the real token is the right one.

### Scenario 4: The routine's idle ceiling, told apart from Cloudflare's

```gherkin
Given the probe behind the tunnel
When sleep is called for 30, 60, 120 and 300 seconds from the NUC through the tunnel
Then the longest that returns on that path is recorded
When the same sleeps are called from the routine
Then the longest that returns on that path is recorded
And a limit the NUC also hits is attributed to Cloudflare, and a limit only the routine hits is attributed to the routine
When every sleep up to 300 returns from the routine
Then "at least 300s" is recorded and nothing longer is attempted
```

`digest_build` takes 21s on this machine and sends no progress. This number says how much
room that is, and it is the design limit for anything like it later.

### Scenario 5: Harry takes the probe's place

```gherkin
Given scenarios 2 to 4 have passed against the probe
And FEAT-260915-2a6ce1 merged and Harry running on the NUC on port 7430
And HARRY_API_TOKEN in the NUC's .env.local, generated with `openssl rand -hex 32`, and not the probe's throwaway
When the harry tunnel is run with --url http://localhost:7430 instead of the probe's port
And `harry-remote` is merged to `main` and the routine set back to it
Then a routine calls digest_list_candidates and receives the weather, the agenda and the headlines
And through the tunnel a request with no Authorization header and one with a wrong token are refused with 401
```

### Scenario 6: It survives the machine, and so does marcel

```gherkin
Given the harry tunnel running as /etc/systemd/system/cloudflared-harry.service, User=shbunder, with --url
And neither config.yml nor config.yaml in any of the five directories, checked immediately before the reboot
When the NUC reboots and nobody logs in
Then the harry tunnel reconnects and a routine reaches Harry again
And marcel's tunnel reconnects, and https://marcel-bot.com/health answers 200
```

A system unit because `Linger=no`. **The reboot also restarts marcel's tunnel**, which is
why marcel is checked again here, and it is also the first observation of FEAT-260915-2a6ce1's
own reboot criterion — tick that one from the same reboot.

## When it degrades

| What breaks | What still happens | What reaches Slack |
|---|---|---|
| The harry tunnel is down | Harry runs; sessions on the NUC reach it over localhost; the routine's call fails | "morning-page has not run today" at 07:00 |
| The routine cannot present the token | Every call refused with 401 | the same sentence |
| The routine never fired | nothing called Harry | the same sentence |
| The NUC is off at 06:30 | nothing runs | the same sentence, from the start-up check when the NUC is back |
| The harry tunnel's credentials are revoked | the hostname returns a Cloudflare error | the same sentence |
| Marcel's tunnel is down | **nothing changes here** — two processes, no shared file | nothing from Harry; marcel's own concern |

**Every failure of this route reaches Slack as one sentence, and that is accepted
deliberately** rather than solved: the watchdog knows a page was not built, not why. The
tablet shows no new page either way. The operator tells them apart in this order, and
`docs/` carries it:

1. `make health` — is Harry up at all?
2. `cloudflared tunnel info harry` — is the tunnel connected?
3. The routine's run log at claude.ai — did it fire, and what did the call return?
4. `make logs` — did a request reach Harry, and was it refused?

While the probe stands in for Harry, `make probe ARGS="calls"` answers step 4 directly.

## The order to do it in, and who does what

| Step | Scenario | Needs the operator for |
|---|---|---|
| 1 | Scenario 1 — the tunnel | creating a public DNS record on their zone |
| 2 | Scenario 2 — the probe behind it | — |
| 3 | Scenario 3 — a routine reaches the probe | their claude.ai account. **If it genuinely cannot, stop: delete the tunnel and its DNS record, delete `spike/harry-remote`, and hand the trigger to the local route with a dated note on FEAT-260912-0f2744 naming it — the deletion straight away, the note only after FEAT-260915-2a6ce1 has merged, since that branch already carries a note on the same file** |
| 4 | Scenario 4 — the ceiling | their claude.ai account |
| 5 | Scenario 5 — Harry behind it | FEAT-260915-2a6ce1 merged, and the real `HARRY_API_TOKEN` placed |
| 6 | Scenario 6 — the system unit, and a reboot | `sudo`, and a reboot |

**Deleting the tunnel** is three things, in this order: stop `cloudflared tunnel run harry`
(`tunnel delete` refuses a tunnel that still has connections), then
`cloudflared tunnel delete harry`, then remove the `harry` CNAME from the `marcel-bot.com`
zone in the Cloudflare dashboard — `cloudflared` has no command that removes a DNS route
it created.

**Starting it while FEAT-260915-2a6ce1 is in flight.** `board.py can-start` refuses: both
touch `docs`. Steps 1 to 4 need nothing from that feature, so this can start with `--force`
on two conditions, which between them cover every file both could write:

- **Documentation goes in `docs/mcp.md`**, and `docs/operating.md` is not touched until
  FEAT-260915-2a6ce1 has merged.
- **Notes on FEAT-260912-0f2744 wait for that merge too.** That branch has already added
  one, and two unmerged notes on the same file conflict.

`scripts/` is no longer shared: the probe's fingerprint shipped on its own, to `main`.
Steps 5 and 6 wait for FEAT-260915-2a6ce1 regardless.
