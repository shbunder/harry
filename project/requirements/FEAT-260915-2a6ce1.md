# Requirements — FEAT-260915-2a6ce1 Harry runs on the NUC, with a dev stack beside the real one

**This page is written to be picked up by a session with no memory of the one that wrote it.**
Everything you need is either here or named here.

## Context & problem

*(Where things stand — the heading `project/CLAUDE.md` asks for, and what it means here.)*

Harry works. It has been run end to end on a laptop: a Claude task's worth of choices went in
and a 39-page newspaper came out on the tablet, with the weather, the day's calendar and
eighteen articles. What has never happened is any of it running in a container, on the NUC,
on its own.

**What is merged and working:**

| | |
|---|---|
| `weather`, `icloud`, `news`, `remarkable` connectors | four sources, each with its own runbook in its `CONNECTOR.md` |
| `digest_list_candidates`, `digest_build` | the two calls a morning is made of |
| `.harry/jobs/morning-page/JOB.md` | the brief the 06:30 task reads, tested on Sonnet and Haiku |
| the deadline watchdog | says in Slack when no page was built by 07:00 |
| `make digest-candidates`, `make digest-dry PICKS=…` | build a page with no server and no push |
| `Dockerfile` | thoughtful and current: WeasyPrint's libraries, Playwright's Chromium, no model tooling, no config baked in |

**What is not there, and you will hit it in the first ten minutes:**

- **`docker-compose.yml` exists and runs one service.** It has `build: .`,
  `restart: unless-stopped`, the `harry-data` volume, `7430:7430`, `TZ: Europe/Brussels`,
  and both env files in the right order. `make up` works today. What it is missing is the
  `harry-dev` service, any way for a per-capability `.env.local` to reach the container, and
  a tag to roll back to — it pins `image: harry:latest`, which is how you find out you cannot
  go back.

  **Extend it; do not rename it to `compose.yaml`.** Two rules are path-scoped to the old
  name — `.claude/rules/secrets-and-config.md` and `.claude/rules/no-model-calls.md` — so a
  rename silently drops both guards, including the one that stops a model credential being
  mounted into the container. If you rename it anyway, change the `paths:` in both rules in
  the same commit.
- **`.env.local` has never been on the NUC.** Three credentials have to get there, and how
  is a decision this feature makes rather than assumes.
- **De Tijd articles are not fetched.** The connector reads its feed; the full text needs a
  signed-in headed browser, which needs a virtual display in the image. That is
  FEAT-260912-9c933f and it is the one Backlog item that changes what goes in the image.
- **`digest_build` sends no progress notification.** It blocks about 90 seconds on a laptop.
  A silent MCP call is aborted at 300 seconds. On a NUC, over a tunnel, that margin is
  thinner than it looks. Backlog, and worth measuring early rather than at 06:30.

## Goals

- Harry runs on the NUC, restarts with the machine, and survives a reboot with its data.
- A **dev stack runs beside the real one** on the same machine, with its own port, its own
  data and its own credentials — so a change can be tried without touching the morning.
- The three credentials reach the NUC without ever being in the repository, in the image, or
  in a shell history.
- A page can be built by hand on the NUC before anything is scheduled.
- Upgrading is one command and going back is another.

## Non-goals

- **The tunnel.** How a Claude scheduled task reaches Harry from outside the house is
  FEAT-260913-fdd33f, and its reader wants it last. This feature ends at "reachable on the
  local network".
- **De Tijd.** Named below because it changes the image, but it is its own feature.
- Any orchestration beyond compose. One machine, two stacks.
- Secrets management beyond a file with the right mode on it. There is one operator.

## The decision this feature turns on

**One image, two compose profiles — not two images.** Written up as an ADR alongside this
page; the argument in short:

The image carries code and nothing else. It already refuses to bake configuration in —
`Dockerfile` copies neither `.env` nor `.env.local`, and says why. Everything that differs
between dev and prod is therefore configuration: which port, which data directory, which
credentials, which capabilities directory, and whether the scheduler runs at all. Two images
would mean two builds, two things to keep in step, and a dev stack that is not the thing
being shipped.

The one real asymmetry is the scheduler: two stacks both running the deadline watchdog would
both alert, and a dev stack should not be able to say "no page today" about a morning the
real one handled. So **dev runs with the scheduler off**, which is a setting rather than a
different image.

## Scenarios

### Scenario 1: A first boot with nothing configured

```gherkin
Given a NUC with docker and this repository and no .env.local anywhere
When `make up` is run
Then Harry starts and answers /health
And weather and news are loaded, because every setting they declare carries a default
And icloud, remarkable and slack are skipped, each naming the setting it is missing
And every tool needing one of those three is skipped, naming the connector
And nothing crashes, because a capability whose configuration is absent disables itself
```

This is not a stub state, it is the real one, and it is the state every credential arrives
into one at a time. **Two of the four sources already work on a bare machine** — that is why
weather is first in the order below and why the first page you build has a weather panel and
headlines but no agenda.

### Scenario 2: The credentials reach the machine

```gherkin
Given the three all-or-nothing credentials — the reMarkable device token, the iCloud
  app-specific password, and (later) the De Tijd browser session
When they are put on the NUC
Then each lives in a `.env.local` beside the capability that needs it, or in the data volume
And none of them is in the repository, in the image, in a compose file that is committed,
  or in a shell command that a history file would keep
And `/health` turns that capability from skipped to loaded without a rebuild
```

**Decide the mechanism before you touch a credential, not at the terminal.** As things stand
a per-capability `.env.local` has no route into the container at all: `.dockerignore` excludes
`**/.env.local` from the image, and the compose file mounts only `harry-data:/data`. The two
options are a bind mount per connector, or `HARRY_<CAPABILITY>_<SETTING>` variables injected
per service — the prefixed spelling exists for exactly this and is documented in
`.claude/rules/secrets-and-config.md`.

**The recommendation is the injected variables**, because they are what the `Dockerfile`
already assumes ("compose injects both as real environment variables, which outrank the dotenv
files"), they keep the image free of any route to a credential file, and they put every secret
in one place a person can audit — the NUC's own root-owned `.env.local`, which compose already
reads.

The De Tijd session cannot be a variable: it is a file, and it lives in the data volume at
mode 600. **The reMarkable token is the dangerous one:** it grants complete read and write
over every document on the tablet, with no scopes and no expiry.

### Scenario 3: A dev stack beside the real one

```gherkin
Given the real stack running on 7430 with the real data volume
When the dev stack is started
Then it listens on a different port, uses a different data directory, and reads its own
  credentials
And its scheduler is off, so it never sends "no page today" about the real morning
And stopping or rebuilding either one leaves the other running
```

The pattern already exists for worktrees: `make worktree` gives each tree its own port and
data directory for exactly this reason. Do the same here rather than inventing a second idea.

### Scenario 4: A page is built by hand before anything is scheduled

```gherkin
Given the four connectors configured on the NUC
When scripts/call_tool.py digest_list_candidates is run inside the container
Then it answers with the weather, the agenda and forty headlines
When a picks file is written and digest_build is called with deliver=false
Then a PDF is written under the data volume and nothing is pushed to the tablet
```

**Not `make`.** The image has no `make` and the `Makefile` is not copied into it — the
`Dockerfile` copies `pyproject.toml`, `uv.lock`, `src/`, `.harry/`, `project/` and `scripts/`
and nothing else. `scripts/call_tool.py` is in the image and is what the `make` targets shell
out to anyway. `out/` is in `.dockerignore`, so set `HARRY_DIGEST_BUILD_OUT_DIR` to a path
under `/data` or the page lands somewhere that does not survive the container.

Do this before the scheduled task exists. It is the whole product, minus the clock, and it
fails in an obvious place.

### Scenario 5: The morning happens without anybody watching

```gherkin
Given a Claude scheduled task that calls digest_list_candidates then digest_build at 06:30
When the page is built and pushed
Then the tablet has one document named for the date, replacing yesterday's if it is still there
And harry_mark_done("morning-page") stops the watchdog reporting a miss
When the task does not fire at all
Then at 07:00 the watchdog says so in Slack, once
```

That last line is load-bearing and already built. An external trigger cannot report its own
absence.

### Scenario 6: Upgrading, and going back

```gherkin
When a new version is deployed
Then it is one command, and the data volume is untouched
When it turns out to be wrong
Then going back to the previous image is one command, and the data volume is still untouched
```

**The compose file pins `image: harry:latest` today, which is exactly the thing this scenario
warns against.** Tag per deploy — `harry:2026-09-16`, or the short commit — and have prod name
a tag while dev tracks `latest`. Nothing enforces that but the runbook, which is why the
runbook has to have it.

### Scenario 7: Room for De Tijd, without building it

```gherkin
When the image is built
Then xvfb is in it, and nothing uses it yet
```

**That one line is all this feature does about De Tijd.** Putting it in now costs a few
megabytes and saves rebuilding the image inside the feature that needs it.

Why it is needed at all, measured rather than guessed: `httpx` and every flavour of headless
Chromium get `403 Blocked` at De Tijd's edge, and only a **headed** browser gets 200 — which
on a machine with no screen means a virtual display. Behind that block is a paywall needing a
subscriber session. All of that is FEAT-260912-9c933f's to build, including the re-login
procedure an operator will need.

## When it degrades

| What breaks | What still happens | What reaches Slack |
|---|---|---|
| A connector's credential is missing or wrong | Harry starts; that capability is skipped and `/health` names the setting | the loader's start-up alert, once per day |
| A source is down at 06:30 | The page renders without that section | that source's own alert |
| The tablet refuses the push | The page is on disk in the data volume and the answer says where | the tablet connector's line, twice-failed |
| The container is restarted mid-build | Nothing half-written survives; the next call starts over | nothing — the watchdog covers a morning that produced no page |
| The NUC was off overnight | The watchdog's start-up check reports the missed deadline when it comes back | "morning-page has not run today" |
| The dev stack is broken | The real one is untouched — different port, different volume, different credentials | nothing from dev; its scheduler is off |

## Out of scope

- The tunnel (FEAT-260913-fdd33f), which its reader wants last.
- De Tijd's connector (FEAT-260912-9c933f) — only its effect on the image is decided here.
- Any CI. There is none, by choice; `make check` before a push is the gate.

## Open questions

- None blocking. Two worth settling with the operator early: whether the dev stack should
  share the real credentials read-only or have its own throwaway ones, and whether prod
  should pin an image tag per deploy or track a branch.

## The order to do it in

1. **Read `docker-compose.yml`, then extend it.** It exists and `make up` works. Scenario 1
   is the acceptance test and it needs no credentials at all — but it is not "everything is
   skipped": weather and news load on a bare machine.
2. **Credentials, one connector at a time**, watching `/health` turn each from skipped to
   loaded. Weather first — it needs none — then news, then iCloud, then the tablet.
3. **A page by hand** (Scenario 4). If this works, everything except the clock works.
4. **The dev profile** beside it (Scenario 3).
5. **The scheduled task** and one real morning (Scenario 5).
6. Then De Tijd, and then the tunnel, in that order.

## A note on how this page was checked

Two of its first claims were wrong when it was written, and both were the kind a stranger
cannot catch: that there was no compose file, and that a bare machine skips every capability.
The first came from an `ls` with three glob patterns where one matched nothing — zsh aborts
the whole command on that, so the "no compose file" conclusion came from a command that never
ran. **The plan verifier found both by checking the tree.** If you change this page, have it
verified the same way rather than trusting the prose, including this paragraph.
